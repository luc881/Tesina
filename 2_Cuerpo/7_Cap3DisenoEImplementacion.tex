En este capítulo se describe cómo se planeó y construyó el sistema. Las tres primeras secciones presentan el diseño general por medio de diagramas: el diagrama de bloques, que muestra las piezas del sistema y cómo se conectan; los casos de uso, que muestran quién puede hacer qué; y el flujo de pantallas, que muestra lo que el usuario ve al usarlo. Las secciones restantes desarrollan la construcción de cada componente en el orden de los objetivos específicos del proyecto: la base de datos, el servidor (API), la interfaz web, el nodo sensor, el gabinete y el lector de código de barras. En cada caso se explica qué se hizo y por qué se decidió hacerlo de esa manera.

% =============================================
% SECCIÓN 3.1: DIAGRAMA DE BLOQUES
% =============================================

\section{Diagrama de bloques}

El primer paso del diseño fue definir qué piezas tendría el sistema y por qué canales se comunicarían, antes de construir cualquiera de ellas. El resultado de esa definición es el diagrama de bloques (Fig.~\ref{fig:cap3-diagrama-bloques}), que se lee de izquierda a derecha en tres columnas: \textbf{entradas}, \textbf{procesos} y \textbf{salidas}.

La columna de \textbf{entradas} contiene los dispositivos que capturan información: el sensor AHT10, que mide la temperatura y la humedad del área de almacenamiento; el lector de código de barras, que captura el código de cada producto durante una venta y lo entrega por USB o Bluetooth; y el equipo del usuario (computadora, tableta o teléfono), desde el que el personal opera el sistema.

La columna central agrupa los \textbf{procesos}, donde la información se transforma y se guarda. El microcontrolador ESP32-C5 recibe las mediciones del sensor a través de la interfaz I\textsuperscript{2}C y las transmite por la red WiFi del establecimiento. La API es el punto de entrada único de todo el sistema: cualquier dato, ya sea una lectura del sensor o una operación de un usuario, pasa por ella, se valida, y se guarda o se consulta en la base de datos.

La columna de \textbf{salidas} muestra los dos destinos de la información. El principal es la interfaz web, que solicita los datos a la API y los presenta con formato en el navegador del usuario. El segundo son las pantallas del propio nodo sensor, que muestran la última lectura directamente en el punto de medición, sin pasar por internet.

Un ejemplo permite recorrer el diagrama completo: una lectura de temperatura nace en el sensor (entrada), pasa por el microcontrolador y la API hasta quedar guardada en la base de datos (procesos), y termina visible tanto en el tablero de la interfaz web como en las pantallas del nodo (salidas). Cada bloque del diagrama se desarrolla a detalle en una sección de este capítulo.

\section{Diagrama de casos de uso}

El siguiente paso del diseño fue delimitar quién lo usaría y qué podría hacer cada quien. Ese análisis se documentó en diagramas de casos de uso, y de él se derivó la estructura de roles y permisos que la base de datos y la API implementan más adelante.

En estos diagramas, las figuras de personas en los extremos son los \textbf{actores}: los tipos de usuario del sistema, más el propio sensor. Los óvalos del centro son las \textbf{funciones} disponibles. Una \textbf{línea sólida} entre un actor y un óvalo significa que ese actor puede ejecutar esa función. Las \textbf{flechas punteadas} señalan funciones opcionales que amplían una función base; usar el escáner, por ejemplo, es una extensión opcional de registrar una venta, no un paso obligatorio.

Dado que el sistema tiene cinco actores y más de veinte funciones, el diagrama se dividió en dos figuras para que se mantenga legible: la Fig.~\ref{fig:cap3-uc-operaciones} cubre la operación diaria del punto de venta y el inventario, y la Fig.~\ref{fig:cap3-uc-administracion} cubre la administración del sistema y el monitoreo ambiental.

En la Fig.~\ref{fig:cap3-uc-operaciones} aparecen los dos actores de la operación diaria. El \textbf{Cajero} registra ventas, consulta el historial, aplica devoluciones y puede usar el escáner de código de barras como función opcional al registrar una venta. El \textbf{Almacenista} gestiona el catálogo de productos, controla los lotes de inventario, registra compras a proveedores y consulta alertas de vencimiento. Las funciones del centro del diagrama están conectadas con ambos actores porque son comunes a los dos perfiles.

La Fig.~\ref{fig:cap3-uc-administracion} completa el panorama con los tres actores restantes. El \textbf{Administrador} hereda todas las funciones del Cajero y el Almacenista (Fig.~\ref{fig:cap3-uc-operaciones}) y añade las funciones exclusivas de gestión: usuarios, roles y permisos, y sucursales. El actor \textbf{Solo lectura} puede consultar toda la información del sistema sin modificar ningún registro. El \textbf{Sensor ESP32} es el único actor no humano: su única función es enviar datos de temperatura y humedad de forma automática, sin intervención de ningún usuario; los usuarios autenticados consultan esas lecturas desde el módulo de monitoreo ambiental.

\section{Flujo de pantallas}

El último elemento del diseño general fue la interacción: antes de programar la interfaz se definió qué pantallas existirían, cómo se llegaría de una a otra y qué patrón repetirían todos los módulos. Esta sección documenta ese diseño mediante un flujo de pantallas, una representación que combina las pantallas del sistema con el recorrido de navegación entre ellas: se ve tanto qué hace el usuario como qué tiene enfrente en cada momento.

En las figuras, el diseño se ilustra con las pantallas ya implementadas en lugar de bocetos, porque permiten ver el recorrido tal como lo vive el usuario final; las pruebas de estos recorridos corresponden al Capítulo 4. Primero se presenta el diagrama de navegación, el mapa general de pantallas, y después se recorre su ruta principal: el registro de una venta.

\subsection{Diagrama de navegación}

Un diagrama de navegación muestra todas las pantallas del sistema y cómo el usuario puede desplazarse entre ellas: cada recuadro representa una pantalla y las líneas indican desde dónde se puede llegar a ella. La Fig.~\ref{fig:cap3-wireflow-general} presenta el diagrama de navegación completo del sistema, y se lee de arriba hacia abajo.

El recorrido siempre inicia en la pantalla de \textbf{Inicio de sesión}, en la parte superior: es la única pantalla accesible sin identificarse, y su única salida conduce al \textbf{Dashboard}. El Dashboard es el centro de la aplicación: de él se desprenden las cuatro ramas que corresponden a los grupos del menú lateral, visibles como columnas en el diagrama:

\begin{itemize}[nosep, itemsep=3pt]
    \item \textbf{General:} las pantallas de Inicio y Estadísticas, con los indicadores del negocio.
    \item \textbf{Punto de venta:} el módulo de Productos, que se subdivide en el listado, el alta de nuevos productos y los catálogos de categorías, marcas, lotes con existencias, fórmulas genéricas y sustancias; el módulo de Ventas; y el Calendario.
    \item \textbf{Operaciones:} los módulos de Devoluciones, Proveedores y Compras.
    \item \textbf{Sistema:} los módulos de Usuarios (incluida la pantalla Mi cuenta del usuario activo), Roles, Sucursales y el monitoreo del Sensor ambiental.
\end{itemize}

Bajo casi todos los módulos se repite el mismo par de pantallas: una \textit{Lista} que muestra los registros existentes y una pantalla \textit{Nueva/Nuevo} para dar de alta un registro. Esta uniformidad es intencional: una vez que el usuario aprende a operar un módulo, sabe operar todos los demás.

\subsection{Recorrido de ejemplo: registro de una venta}

A continuación se recorre, con las pantallas reales del sistema, la ruta \textit{Inicio de sesión} → \textit{Dashboard} → \textit{Ventas} → \textit{Nueva} trazada sobre el diagrama de navegación (Fig.~\ref{fig:cap3-wireflow-general}). Se eligió el registro de una venta por ser el flujo principal del sistema y el más representativo de la interacción diaria en el punto de venta; los demás módulos siguen una estructura similar, con un listado general y la opción de crear, editar o consultar el detalle de cada registro. 

El recorrido inicia en el inicio de sesión (Fig.~\ref{fig:cap3-wireflow-login}), único punto de entrada al sistema. Con el acceso correcto se llega al \textbf{Dashboard} (Fig.~\ref{fig:cap3-wireflow-dashboard}), donde el cajero selecciona \textit{Ventas} en el menú lateral y abre el formulario de nueva venta (Fig.~\ref{fig:cap3-wireflow-ventas}); ahí los productos se agregan buscándolos por nombre o con la tecla \textbf{F2}, que activa el \textbf{modo lector} para escanearlos con el lector de código de barras. Al confirmar (Fig.~\ref{fig:cap3-wireflow-completar}), el sistema descuenta el inventario y conserva el detalle de la transacción para consultas posteriores.

La Fig.~\ref{fig:cap3-wireflow-modulos} muestra los módulos restantes, accesibles desde el menú lateral y con la misma estructura de listado con buscador.

\section{Desarrollo de la base de datos en PostgreSQL}

Para cumplir con el primer objetivo específico se diseñó e implementó una base de datos relacional en PostgreSQL que centraliza toda la información del sistema: productos, lotes de inventario, usuarios, ventas y mediciones ambientales. El esquema resultante comprende \textbf{22 tablas} agrupadas en cinco módulos funcionales.

\subsection{Selección de PostgreSQL}

Se eligió PostgreSQL como sistema gestor de base de datos por ser la opción recomendada por las herramientas utilizadas en el proyecto y por su amplia adopción en aplicaciones web profesionales. Frente a alternativas como MySQL o SQLite ofrece además una ventaja concreta para este sistema: su tipo de dato \textbf{NUMERIC} almacena cantidades monetarias con precisión exacta, sin los pequeños errores de redondeo que otros formatos numéricos acumulan al operar con decimales. En un sistema que calcula totales de ventas, esa exactitud es indispensable.

\subsection{Organización modular del esquema}

Las 22 tablas se dividieron en cinco módulos según el área del negocio que gestionan, de modo que cada módulo tenga una responsabilidad clara y las dependencias entre módulos sean explícitas:

\begin{enumerate}[nosep, itemsep=3pt]
    \item \textbf{Autenticación y control de acceso:} usuarios, roles y permisos.
    \item \textbf{Catálogo de productos:} información de los medicamentos y sus características.
    \item \textbf{Inventario y compras:} lotes, fechas de caducidad y órdenes de abastecimiento.
    \item \textbf{Registro de ventas:} transacciones, pagos y devoluciones.
    \item \textbf{Mediciones del sensor:} lecturas de temperatura y humedad.
\end{enumerate}

Esta separación hace que las tablas de un módulo puedan crecer o modificarse sin impactar innecesariamente a los demás, y permite localizar con facilidad qué parte del esquema es responsable de cada tipo de dato.

Este módulo agrupa cinco tablas: usuarios, roles, permisos, la relación entre roles y permisos, y sucursales. El acceso se estructuró por roles: cada usuario pertenece a un rol (\textit{administrador}, \textit{cajero}) y el rol define qué operaciones puede realizar, de modo que cambiar los privilegios de un grupo requiere modificar solo el rol y no cada cuenta.

\section{Desarrollo de la API REST con FastAPI}

Para cumplir con el segundo objetivo específico se diseñó e implementó una API REST en Python con el \textit{framework} FastAPI. La API actúa como intermediario entre los clientes y la base de datos: recibe peticiones, las procesa y devuelve la información en un formato que ambos clientes pueden interpretar.      

\subsection{Selección de FastAPI}

Se eligió FastAPI sobre alternativas como Flask o Django por dos razones.

La primera es que verifica automáticamente que los datos que llegan en cada petición sean correctos antes de procesarlos. Si algo no cumple lo esperado, rechaza la petición con un mensaje descriptivo sin necesidad de escribir ese código de validación manualmente.

La segunda es que genera automáticamente una página de documentación interactiva donde se puede ver cada operación disponible, sus parámetros y las posibles respuestas. Esto permitió verificar el funcionamiento de la API directamente desde el navegador durante el desarrollo, sin herramientas adicionales.

\subsection{Arquitectura en capas}

La API se diseñó como una serie de filtros por los que pasa cada petición antes de poder interactuar con la base de datos. Se separó en filtros distintos porque cada uno tiene una responsabilidad diferente: si en algún momento cambia una regla de seguridad o una validación del negocio, solo se modifica ese filtro sin tocar el resto.

El primer filtro actúa como un enrutador: dependiendo de la dirección de la petición, determina a qué operación corresponde y la redirige al área correspondiente, de forma similar a como un router de red decide por qué camino enviar el tráfico. El segundo filtro verifica que el usuario esté identificado y que tenga permiso para realizar esa operación; si no cumple alguna de las dos condiciones, la petición es rechazada sin continuar. El tercero aplica las reglas del negocio, como confirmar que hay existencias suficientes antes de registrar una venta. El último ejecuta la operación sobre la base de datos y devuelve el resultado al cliente.

\subsection{Modelos ORM con SQLAlchemy}

Para interactuar con la base de datos desde el código Python se decidió representar cada tabla del esquema como una clase. Así se trabaja con objetos en lugar de instrucciones SQL escritas a mano, y la definición del esquema queda centralizada en un único lugar: cualquier modificación (agregar una columna, renombrar un campo) se aplica una sola vez y se refleja en toda la aplicación.

Como ejemplo, el siguiente fragmento del código de la API muestra la clase que representa la tabla de lotes de inventario:\newpage

\begin{lstlisting}[language=Python]
class ProductBatch(Base):
    __tablename__ = "product_batches"

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True)
    product_id: Mapped[int] = mapped_column(
        ForeignKey("products.id"), nullable=False, index=True)
    lot_code: Mapped[Optional[str]] = mapped_column(
        String(100), nullable=True)
    expiration_date: Mapped[Optional[date]] = mapped_column(
        Date, nullable=True)
    quantity: Mapped[int] = mapped_column(Integer, nullable=False)

    product = relationship("Product", back_populates="batches")
\end{lstlisting}

La primera línea declara el nombre de la tabla y cada atributo de la clase corresponde a una columna con su tipo de dato y sus reglas: \texttt{nullable=False} marca la cantidad como obligatoria, \texttt{nullable=True} deja que el código de lote y la caducidad queden vacíos (el caso de los lotes sin código descrito en la sección de la base de datos), y \texttt{ForeignKey} enlaza cada lote con el producto al que pertenece. La última línea define la relación en ambos sentidos: desde un lote se puede consultar su producto y desde un producto todos sus lotes.

Con esta definición, al iniciar la aplicación se obtiene en PostgreSQL la tabla \texttt{product\_batches} con sus columnas, tipos y restricciones exactamente como se declararon en la clase, sin haber escrito ninguna instrucción SQL. El resto de las 22 tablas del esquema se define de la misma manera.

\subsection{Validación de los datos de entrada}

Para cada operación de la API se definió un contrato: qué información acepta cuando el cliente envía datos, qué campos son obligatorios y qué estructura tiene la respuesta. Si una petición no cumple ese contrato (un precio negativo, un campo requerido ausente) se rechaza antes de llegar a la lógica de la aplicación, sin código de validación manual adicional.


\subsection{Autenticación y autorización}

El diseño del control de acceso partió de dos requisitos: que cada petición pudiera verificarse sin consultar la base de datos, para no sumar una consulta adicional a cada operación del sistema, y que los permisos definidos en la base de datos fueran exactamente los que se aplican al momento de operar.

Para el primer requisito se decidió usar \textbf{tokens firmados}. Al iniciar sesión, la API verifica la contraseña (que se almacena cifrada, nunca en texto legible) y emite un token de sesión con vigencia de 30 minutos que lleva dentro la identidad y los permisos del usuario; como el token va firmado, el servidor confía en su contenido sin volver a consultar la base de datos. La vigencia se fijó corta a propósito, para limitar el daño si un token llegara a ser interceptado. Y para que esa vigencia corta no obligue al usuario a escribir su contraseña cada 30 minutos, se emite también un token de renovación válido por 7 días, con el que la sesión se extiende en segundo plano.

Para el segundo requisito, la \textbf{autorización}, se decidió que cada operación de la API declare el permiso que exige y lo compruebe contra el token antes de ejecutarse. Así, la estructura de roles definida en la base de datos se aplica en cada petición: un cajero puede registrar ventas, pero no modificar usuarios ni configurar sucursales. \subsection{Autenticación en el cliente}

La API exige un token en cada petición y ese token caduca a los 30 minutos, de modo que al diseñar la interfaz hubo que resolver tres problemas: dónde guardar el token, cómo incluirlo en todas las peticiones sin repetir código en dieciséis módulos, y cómo renovarlo sin interrumpir al usuario.

La decisión fue concentrar toda la gestión de la sesión en una sola función, en lugar de repartirla por la aplicación. Esa función guarda el token en el almacenamiento del navegador, lo registra como encabezado por defecto de todas las peticiones y programa su renovación automática leyendo la fecha de caducidad que el propio token trae dentro. El siguiente fragmento del código de la interfaz muestra esa función; se ejecuta al iniciar sesión con el token recibido, y al cerrar sesión sin token:

\begin{lstlisting}
export async function setSession(accessToken) {
  if (accessToken) {
    sessionStorage.setItem(JWT_STORAGE_KEY, accessToken);
    axios.defaults.headers.common.Authorization =
      `Bearer ${accessToken}`;

    const decoded = jwtDecode(accessToken);
    if (decoded?.exp) scheduleTokenRefresh(decoded.exp);
  } else {
    sessionStorage.removeItem(JWT_STORAGE_KEY);
    delete axios.defaults.headers.common.Authorization;
  }
}
\end{lstlisting}

Cuando recibe un token, la función ejecuta los tres pasos del diseño (guardar, registrar como encabezado, programar la renovación); cuando se llama sin token, los revierte y la sesión queda cerrada.

Con esto, ningún otro componente tiene que ocuparse de la autenticación: los dieciséis módulos hacen sus peticiones sin mencionar el token y la renovación ocurre en segundo plano, sin que el usuario vuelva a escribir su contraseña. Sobre esta misma base se protegieron las rutas de la aplicación: si no hay sesión activa, cualquier intento de abrir una pantalla redirige al inicio de sesión, y las operaciones que exigen permisos específicos comprueban que el token los incluya, en línea con la estructura de roles del sistema.

\section{Desarrollo del nodo sensor con ESP32}

Para cumplir con el cuarto objetivo específico se diseñó e implementó un nodo electrónico que mide temperatura y humedad relativa en el área de almacenamiento y envía esas lecturas a la API del sistema. El nodo está integrado por un microcontrolador \textbf{ESP32-C5}, un sensor \textbf{AHT10} y tres pantallas \textbf{OLED SSD1306}, programado en C++ con el entorno Arduino.

\subsection{Selección del hardware}

Se eligió el \textbf{ESP32-C5} como microcontrolador por tres razones: integra conectividad WiFi de forma nativa sin necesitar un módulo adicional, soporta el protocolo I\textsuperscript{2}C necesario para comunicarse con el sensor y las pantallas, y es compatible con el entorno Arduino, que provee bibliotecas maduras para red y manejo de datos. Se descartó el Arduino Uno por carecer de WiFi integrado. Una Raspberry Pi, por su parte, habría resultado sobredimensionada para leer y enviar dos valores numéricos periódicamente: cuesta y consume más sin aportar un beneficio funcional que lo justifique.

Para la medición ambiental se eligió el sensor \textbf{AHT10} sobre alternativas como el DHT11 o el DHT22 por dos razones. La primera es que se comunica por I\textsuperscript{2}C, la misma interfaz que usan las pantallas, con solo dos conductores por conexión. La segunda es su precisión de ±0.3\,°C en temperatura y ±2\% en humedad, suficiente para vigilar los límites de 30\,°C y 65\% de humedad relativa que la normativa sanitaria marca como máximos para el almacenamiento de medicamentos.

\subsection{Arquitectura del nodo}

\subsection{Funcionamiento del firmware}

El firmware se estructuró según el modelo de Arduino: una función de configuración que se ejecuta una sola vez al encender el dispositivo (inicializa los buses I\textsuperscript{2}C, detecta el sensor y establece la conexión WiFi) y un ciclo continuo que realiza las lecturas cada 30 segundos y las envía a la API. Para la espera entre lecturas se decidió no pausar el programa, sino comparar continuamente el tiempo transcurrido: así el ciclo puede vigilar la conexión WiFi y el botón de reinicio en cada vuelta, en lugar de quedarse congelado 30 segundos.

Para la conexión WiFi se utilizó la biblioteca \textbf{WiFiManager}. En el primer arranque, el ESP32 crea una red temporal de nombre \texttt{Sensor-Farmacia}; el técnico se conecta desde un teléfono o computadora, selecciona la red del establecimiento e ingresa la contraseña. El dispositivo guarda esas credenciales y las usa automáticamente en arranques posteriores. Si se necesita cambiar la red (por ejemplo, al reubicar el dispositivo), mantener presionado el botón de reinicio durante tres segundos borra las credenciales y reinicia el proceso de configuración.

El corazón del firmware es la función que se ejecuta en cada ciclo de lectura. El siguiente fragmento es su código tal como opera en el nodo:

\begin{lstlisting}[language=C++]
void leerYEnviar() {
  Wire.end(); Wire.begin(SDA_AHT, SCL_AHT);
  sensors_event_t humEv, tempEv;
  aht.getEvent(&humEv, &tempEv);

  float t = tempEv.temperature;
  float h = humEv.relative_humidity;

  if (t < -10 || t > 85 || h < 0 || h > 100) {
    Serial.printf("Fuera de rango: %.1fC %.1f%%\n", t, h);
    return;
  }

  mostrarTemperatura(t);
  mostrarHumedad(h);
  if (wifiOk) enviarLectura(t, h);
}
\end{lstlisting}

La función realiza cuatro pasos. Primero activa el canal de comunicación del sensor y le solicita las dos mediciones. Después valida que los valores estén dentro del rango físicamente posible del sensor (de $-10$ a $85\,^\circ$C y de 0 a 100\,\% de humedad); si una lectura cae fuera, se descarta y la función termina sin enviar nada, para que un fallo momentáneo del sensor no registre datos falsos. En seguida actualiza las pantallas OLED con los valores medidos. Por último, solo si hay conexión WiFi, envía la lectura a la API.

Lo que se obtiene en cada ciclo es un mensaje en formato JSON, por ejemplo \texttt{\{"temperature": 23.4, "humidity": 41.2, "device\_id": "esp32-farmacia-01"\}}, que la API almacena en la base de datos como se mostró en la sección de la API, y que aparece segundos después en el tablero de la aplicación web.

El envío se realiza mediante una petición cifrada (HTTPS). El intervalo de 30 segundos entre lecturas balancea el detalle del historial con la carga sobre la red: lecturas más frecuentes no aportarían información adicional relevante para el monitoreo ambiental de un almacén.

Las figuras~\ref{fig:cap3-firmware-setup} y~\ref{fig:cap3-firmware-loop} presentan en diagrama de flujo el comportamiento completo del firmware, separado en sus dos etapas. La Fig.~\ref{fig:cap3-firmware-setup} corresponde a la \textbf{secuencia de arranque}, que se ejecuta una sola vez al encender el nodo: se inicializan los buses de comunicación y las pantallas, se detecta el sensor, se establece la conexión WiFi mediante el portal de configuración (con tres minutos como tiempo límite) y, si el sensor respondió, se realiza una primera lectura antes de entrar al ciclo. Los rombos del diagrama son puntos de decisión: cuando el sensor o el WiFi no están disponibles, el arranque no se detiene, sino que registra la falla y continúa, de modo que el nodo siga mostrando en pantalla lo que sí puede medir.

La Fig.~\ref{fig:cap3-firmware-loop} corresponde al \textbf{ciclo operativo}, que se repite de forma continua mientras el nodo está encendido. Cada iteración verifica primero si el botón de reinicio lleva más de tres segundos presionado, en cuyo caso borra las credenciales WiFi y reinicia el equipo; después comprueba si ya transcurrieron los 30 segundos del intervalo de lectura. Cuando el intervalo se cumple, lee el sensor, valida que los valores estén dentro del rango físico admisible, actualiza las pantallas y, si hay conexión, envía la lectura a la API. Las salidas marcadas con \textit{No} en los rombos regresan por el carril izquierdo al inicio del ciclo: una lectura inválida o la falta de red no detienen el programa, solo omiten el envío de esa iteración.

\subsection{Pantallas OLED}

Se incorporaron tres pantallas \textbf{OLED SSD1306} de 128×64 píxeles para que el personal pueda verificar el estado del nodo (temperatura, humedad y conexión WiFi) sin necesidad de abrir la aplicación web; cada pantalla muestra un único dato para que sea legible de un vistazo. Como los módulos vienen de fábrica con una dirección I\textsuperscript{2}C fija que no puede modificarse, las tres pantallas no pueden compartir una sola línea de comunicación: cada una opera en un bus I\textsuperscript{2}C independiente del ESP32-C5, separado también del bus que usa el sensor. La actualización ocurre tras cada ciclo de lectura, reutilizando el mismo dato que se envía a la API sin operaciones adicionales.

\section{Diseño e impresión del gabinete físico}

El quinto objetivo específico consistió en diseñar y fabricar el gabinete que aloja el ESP32, el sensor AHT10 y las tres pantallas OLED en un conjunto compacto y protegido. Se optó por un diseño a medida fabricado mediante \textbf{impresión 3D} porque la alineación horizontal de tres módulos OLED no corresponde a ninguna caja disponible comercialmente, y adaptar una caja genérica habría requerido cortes imprecisos y un acabado poco profesional.

El gabinete se compone de dos piezas: una base que aloja la tarjeta del microcontrolador y el cableado interno, y una tapa frontal con tres ventanas rectangulares para exponer las pantallas OLED. Una abertura lateral permite la salida del cable de alimentación USB. Las dos piezas ensamblan a presión, sin tornillos.

Cada decisión de diseño respondió a una restricción práctica. El ensamble a presión se eligió porque los componentes internos pueden requerir ajuste durante la vida útil del dispositivo: con tornillos, el acceso repetido desgasta las roscas en plástico impreso, mientras que el encaje a presión tolera abrir y cerrar el gabinete sin deteriorarse. El ancho mínimo lo determinaron los tres módulos OLED dispuestos en fila horizontal con sus conectores orientados hacia la base. La ventilación del sensor AHT10 se resolvió con una ranura en la base, suficientemente pequeña para evitar la entrada de polvo pero que permite la circulación del aire del área de almacenamiento.

\section{Integración del lector de código de barras}

El sexto objetivo específico consistió en incorporar un lector de código de barras al flujo de registro de ventas de la aplicación web. Se eligió un lector USB que el sistema operativo reconoce como un teclado estándar: desde la perspectiva del navegador, el código escaneado se ingresa como si hubiera sido tecleado manualmente, lo que evitó desarrollar cualquier controlador o integración especial.

El flujo estándar de creación de venta no estaba diseñado para el ritmo de escaneo continuo: el operador habría tenido que hacer clic en el campo correcto y esperar el resultado por cada artículo. Para que la herramienta resultara práctica en un punto de venta, se diseñó un \textbf{modo lector} en el módulo de ventas, activable desde cualquier parte del formulario con la tecla \textbf{F2}, que redirige el foco al campo de lectura sin que el usuario tenga que desplazarse.

La búsqueda del código se diseñó para resolverse localmente: el catálogo de productos se carga en memoria al abrir el formulario y cada código escaneado se compara contra él, sin generar una petición al servidor por artículo. Esto evita la latencia de red en un flujo donde varios artículos se escanean en secuencia rápida. Si hay coincidencia, el producto se agrega a la venta; si no la hay, el campo muestra una señal de error. El modo se desactiva automáticamente al hacer clic fuera del área de escaneo.

Con esto quedan descritos el diseño y la construcción de los seis componentes planteados en los objetivos: la base de datos, la API, la interfaz web, el nodo sensor, su gabinete y la integración del lector. El Capítulo 4 documenta las pruebas a las que se sometió cada componente y los ajustes que resultaron de ellas.
