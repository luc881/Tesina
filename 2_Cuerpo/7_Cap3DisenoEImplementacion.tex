En este capítulo se describe el proceso de diseño e implementación del sistema de gestión de inventario y ventas con monitoreo ambiental para la Farmacia Selene. Se presentan las decisiones tomadas en cada etapa del desarrollo, desde la estructuración de la base de datos y la construcción de la API hasta la implementación de la interfaz web y el nodo de sensores, así como el proceso de integración y despliegue del sistema completo.




% =============================================
% SECCIÓN 1: ARQUITECTURA GENERAL
% =============================================

\section{Arquitectura general del sistema}

El sistema fue diseñado siguiendo una arquitectura de tres capas que separa responsabilidades de manera clara y facilita el mantenimiento y la escalabilidad del proyecto. Esta separación permite que cada capa evolucione de manera independiente sin afectar el funcionamiento de las demás.

La \textbf{Capa Frontend} constituye la interfaz de usuario accesible desde el navegador web. Es la parte visible del sistema, desde la cual los empleados y administradores de la farmacia consultan el inventario, registran ventas y visualizan alertas ambientales. Esta capa fue desarrollada con React y Material-UI, y está desplegada en la plataforma Vercel.

La \textbf{Capa Backend} actúa como núcleo del sistema. Contiene la lógica de negocio, gestiona la autenticación de usuarios y expone una API REST desarrollada con FastAPI que permite la comunicación con el frontend y con los dispositivos físicos. El servidor se encuentra alojado en Railway junto con la base de datos PostgreSQL.

La \textbf{Capa Física} está compuesta por el microcontrolador ESP32-C5 y el sensor de temperatura y humedad AHT10. Este nodo captura variables ambientales del área de almacenamiento de medicamentos y las envía periódicamente al backend mediante solicitudes HTTP sobre la red Wi-Fi de la farmacia.

La comunicación entre capas se realiza mediante el formato JSON a través de la API REST. La Figura~\ref{fig:cap3-estructura} ilustra la organización general del sistema y la relación entre sus componentes.

\section{Diseño e implementación de la API REST}

La API REST constituye el punto de comunicación central del sistema. Fue desarrollada con \textbf{FastAPI} y se encarga de recibir solicitudes del frontend y del nodo sensor, procesarlas conforme a las reglas del negocio y devolver respuestas en formato JSON. La API se encuentra desplegada en Railway y es accesible de forma pública mediante un dominio asignado por la plataforma.

\begin{figure}[H]
    \centering
    \fbox{\includegraphics[width=0.85\textwidth]{0_imagenes/Avances1/APIDominio.png}}
    \caption{Dominio público de la API del sistema}
    \label{fig:cap3-api-dominio}

    \vspace{0.2cm}
    \footnotesize \textbf{Fuente:} Elaboración propia.
\end{figure}

\subsection{Organización de los endpoints}

La API cuenta con aproximadamente \textbf{48 endpoints} organizados en módulos que agrupan las operaciones según su área funcional:

\begin{itemize}
    \item \textbf{Autenticación:} inicio de sesión y generación de tokens JWT.
    \item \textbf{Usuarios:} creación, consulta, modificación y eliminación de cuentas.
    \item \textbf{Productos:} gestión del catálogo de medicamentos.
    \item \textbf{Inventario:} consulta y actualización de existencias.
    \item \textbf{Ventas:} registro y consulta de transacciones.
    \item \textbf{Sensores:} recepción y consulta de mediciones ambientales.
\end{itemize}

\subsection{Autenticación con JWT}

Para controlar el acceso a la API se implementó un sistema de autenticación basado en \textbf{JSON Web Tokens (JWT)}. Cuando un usuario inicia sesión con credenciales válidas, el servidor genera un token firmado digitalmente que debe incluirse en el encabezado de cada solicitud posterior. Únicamente las solicitudes que presenten un token válido y vigente son procesadas por los endpoints protegidos.

Este mecanismo garantiza que solo los usuarios autenticados puedan consultar o modificar la información del sistema, independientemente de la red desde la que realicen la solicitud.

FastAPI genera automáticamente documentación interactiva de la API en formato OpenAPI, lo que facilitó las pruebas durante el desarrollo y permite verificar el comportamiento de cada endpoint sin necesidad de herramientas externas.

\section{Implementación del nodo de monitoreo ambiental}

El nodo de monitoreo ambiental está compuesto por el microcontrolador \textbf{ESP32-C5} y el sensor \textbf{AHT10}, programados en C++ mediante el Arduino IDE. Su función es medir periódicamente la temperatura y la humedad del área de almacenamiento de medicamentos y enviar los datos al backend mediante solicitudes HTTP.

\subsection{Flujo de operación del nodo}

El firmware del ESP32-C5 sigue el siguiente ciclo de operación:

\begin{enumerate}
    \item Al encender el dispositivo, se intenta establecer conexión con la red Wi-Fi cuyas credenciales están almacenadas en la memoria no volátil del microcontrolador.
    \item Si no se encuentran credenciales guardadas o la conexión falla, se activa el portal de configuración de \textbf{WiFiManager}, que genera un punto de acceso temporal llamado \texttt{PharmaTrack-Sensor} para que el usuario ingrese las credenciales desde un navegador.
    \item Una vez conectado a la red, el microcontrolador lee los valores de temperatura y humedad del sensor AHT10 mediante la interfaz I²C.
    \item Los datos son empaquetados en formato JSON y enviados al endpoint de sensores de la API mediante una solicitud HTTP POST.
    \item El proceso de lectura y envío se repite periódicamente en intervalos definidos en el firmware.
\end{enumerate}

\subsection{Mecanismo de restablecimiento de credenciales}

Para facilitar el mantenimiento del dispositivo, se implementó un mecanismo de restablecimiento mediante el botón BOOT del ESP32-C5 (GPIO~0). Al mantenerlo presionado durante más de tres segundos, el sistema borra las credenciales Wi-Fi almacenadas y reinicia el portal de configuración, permitiendo configurar una nueva red sin necesidad de recompilar ni reprogramar el microcontrolador.

Este diseño reduce la dependencia de personal técnico especializado para tareas de reconfiguración, lo que es especialmente relevante en el entorno operativo de una pequeña farmacia.

Antes de importar los datos fue necesario realizar un proceso de limpieza y estandarización, ya que el archivo presentaba inconsistencias comunes en registros administrados manualmente:

\begin{itemize}
    \item Registros duplicados de productos.

\section{Despliegue e integración del sistema}

El despliegue del sistema se realizó en dos plataformas de nube independientes que trabajan de manera coordinada para mantener todos los componentes del sistema disponibles de forma continua.

El \textbf{backend y la base de datos} fueron desplegados en \textbf{Railway}. La plataforma gestiona automáticamente la ejecución del servidor FastAPI y la instancia de PostgreSQL, ofreciendo herramientas de monitoreo para verificar el estado del servicio y detectar posibles errores en tiempo real.

La \textbf{interfaz web} fue desplegada en \textbf{Vercel}, que conecta directamente con el repositorio del proyecto. Cada actualización del código del frontend genera automáticamente una nueva versión publicada, lo que facilita el ciclo de desarrollo y garantiza que los usuarios siempre accedan a la versión más reciente del sistema.

El \textbf{nodo sensor} opera de forma autónoma dentro de la red local de la farmacia, enviando datos de forma periódica a la API alojada en Railway sin requerir intervención manual.

La integración entre estas tres capas queda definida por los contratos de la API REST: el frontend y el nodo sensor conocen únicamente las rutas, los formatos de solicitud y las respuestas esperadas, de modo que cada componente puede actualizarse o reemplazarse de manera independiente sin afectar el funcionamiento del sistema completo.
