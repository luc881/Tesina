\section{Desarrollo de la base de datos en PostgreSQL}

El primer objetivo específico consistió en diseñar e implementar la base de datos que centraliza la información del sistema: productos, niveles de inventario, usuarios, registros de ventas y mediciones de los sensores. La base de datos resultante está compuesta por \textbf{22 tablas} organizadas en cinco módulos funcionales, cuya evolución fue gestionada mediante \textbf{13 migraciones} con Alembic.

\subsection{Selección de PostgreSQL}

Se eligió PostgreSQL como sistema gestor de base de datos por tres razones técnicas principales. Primero, garantiza el cumplimiento de las propiedades ACID (Atomicidad, Consistencia, Aislamiento y Durabilidad), lo cual es indispensable en un sistema que registra transacciones financieras y movimientos de inventario donde una operación interrumpida no debe dejar el estado de la base de datos en un punto inconsistente. Segundo, provee el tipo de dato \texttt{NUMERIC(p,s)}, que almacena valores decimales con precisión exacta; esto es relevante porque los tipos de punto flotante (\texttt{DOUBLE}, \texttt{FLOAT}) acumulan errores de representación binaria que producen inexactitudes al sumar totales monetarios. Tercero, soporta índices únicos parciales, una funcionalidad que se aprovechó específicamente para el control de lotes de productos, como se explica más adelante.

\subsection{Estructura modular del esquema}

El esquema fue organizado en cinco módulos con responsabilidades bien delimitadas, de modo que las tablas de cada módulo gestionen una sola área del negocio y las dependencias entre módulos sean explícitas mediante llaves foráneas.

\subsubsection*{Módulo de autenticación y control de acceso}

Este módulo gestiona la identidad de los usuarios y sus permisos dentro del sistema. Está formado por cuatro tablas: \texttt{users}, \texttt{roles}, \texttt{permissions} y la tabla pivote \texttt{role\_has\_permissions}. Se implementó el patrón \textbf{RBAC} (\textit{Role-Based Access Control}), en el que cada usuario tiene un rol asignado y cada rol agrupa un conjunto de permisos. Esta separación entre rol y permiso permite modificar los privilegios de un grupo de usuarios cambiando únicamente el rol, sin necesidad de actualizar cada cuenta individualmente.

La tabla \texttt{users} incluye la columna \texttt{deleted\_at} para soportar \textbf{borrado lógico} (\textit{soft delete}): en lugar de eliminar físicamente el registro de un usuario, se registra la fecha de baja. Esta decisión se tomó porque el historial de ventas referencia al usuario que las realizó; eliminar físicamente el registro rompería la integridad referencial o requeriría valores nulos en columnas que representan información operativa. El mismo patrón se aplicó a las tablas \texttt{roles}, \texttt{products}, \texttt{branches} y \texttt{sale\_payments}.

\subsubsection*{Módulo de catálogo de productos}

Este módulo almacena la información de los medicamentos y está compuesto por seis tablas: \texttt{products}, \texttt{product\_master}, \texttt{product\_categories}, \texttt{product\_brands}, \texttt{ingredients} y \texttt{product\_has\_ingredients}.

La tabla \texttt{product\_master} representa el \textbf{medicamento genérico}, mientras que \texttt{products} representa sus presentaciones concretas (tabletas, jarabe, inyectable). Esta separación permite agrupar variantes del mismo principio activo bajo una entidad común, facilitando búsquedas y reportes por nombre genérico sin duplicar información.

La tabla \texttt{product\_categories} implementa una \textbf{jerarquía propia} mediante la columna \texttt{parent\_id} que referencia la misma tabla, lo que permite representar categorías anidadas (por ejemplo: \textit{Medicamentos} → \textit{Analgésicos} → \textit{Antiinflamatorios}) sin requerir una tabla adicional por nivel.

La tabla pivote \texttt{product\_has\_ingredients} registra la relación muchos a muchos entre productos e ingredientes activos, incluyendo la cantidad (\texttt{amount}) y la unidad de medida (\texttt{unit}). Esto hace posible consultar la composición de cualquier producto directamente desde la base de datos.

\subsubsection*{Módulo de inventario y compras}

Este módulo controla las existencias físicas y el abastecimiento mediante tres tablas: \texttt{product\_batches}, \texttt{purchases} y \texttt{purchase\_details}, además de \texttt{suppliers}.

La tabla central es \texttt{product\_batches}, que registra cada \textbf{lote} de producto con su código de lote (\texttt{lot\_code}), fecha de caducidad (\texttt{expiration\_date}) y cantidad disponible (\texttt{quantity}). Esta granularidad es técnicamente necesaria en una farmacia porque los medicamentos tienen fecha de caducidad por lote y las regulaciones farmacéuticas exigen que las salidas respeten el principio \textbf{FEFO} (\textit{First Expired, First Out}): se despacha primero el lote que vence antes.

Para la columna \texttt{lot\_code} se implementó un \textbf{índice único parcial} con la condición \texttt{WHERE lot\_code IS NOT NULL}. Esta decisión resuelve un problema concreto: algunos productos ingresan sin número de lote asignado, por lo que se permiten múltiples entradas con \texttt{lot\_code = NULL} para el mismo producto, pero no se permiten dos lotes con el mismo código no nulo para un mismo producto. Un índice único convencional rechazaría los valores nulos múltiples, lo que haría inviable registrar ingresos sin lote.

Cuando se registra una compra, los datos del pedido quedan en \texttt{purchases} y \texttt{purchase\_details}, y se crea o actualiza el lote correspondiente en \texttt{product\_batches}. Esta distinción entre el documento de compra y el registro de existencias mantiene el historial de abastecimiento independiente del estado actual del inventario.

\subsubsection*{Módulo de ventas}

Este módulo registra las transacciones comerciales mediante cinco tablas: \texttt{sales}, \texttt{sale\_details}, \texttt{sale\_batch\_usage}, \texttt{sale\_payments} y \texttt{refund\_products}.

Se utilizó un diseño de \textbf{cabecera-detalle}: \texttt{sales} almacena los datos generales de la transacción (usuario, sucursal, subtotal, descuento, impuesto, total y estado) y \texttt{sale\_details} registra cada línea de producto vendido. Esta estructura es estándar en sistemas de punto de venta porque permite que una sola venta incluya múltiples productos sin redundar los datos generales de la transacción.

La tabla \texttt{sale\_batch\_usage} establece qué cantidad de qué lote se consumió por cada línea de venta. Esto proporciona \textbf{trazabilidad completa}: dado un número de lote o un producto, es posible consultar en qué ventas específicas fue despachado. Esta información es relevante ante un retiro de mercado o alerta sanitaria sobre un lote defectuoso.

La columna \texttt{status} de \texttt{sales} es un tipo enumerado con los valores \texttt{DRAFT}, \texttt{COMPLETED} y \texttt{CANCELLED}. El estado \texttt{DRAFT} permite acumular los productos de una venta antes de confirmarla, sin afectar el inventario hasta que la transacción sea completada, evitando descuentos prematuros de existencias.

La tabla \texttt{sale\_payments} está separada de \texttt{sales} para soportar \textbf{pagos mixtos}: una misma venta puede liquidarse con efectivo y tarjeta simultáneamente, registrando cada pago como una fila independiente con su método e importe.

\subsubsection*{Módulo de monitoreo ambiental}

La tabla \texttt{sensor\_readings} almacena cada medición enviada por el nodo ESP32-C5, registrando la temperatura, la humedad, la marca de tiempo (\texttt{recorded\_at}) y un identificador de dispositivo (\texttt{device\_id}) en formato cadena de texto. Se optó por no crear una tabla separada de dispositivos dado que el sistema opera con un único nodo sensor; el identificador como cadena permite incorporar nodos adicionales sin modificar el esquema.

\subsection{Gestión de cambios con Alembic}

El esquema no fue diseñado de forma estática, sino que evolucionó de manera iterativa a lo largo del desarrollo. Para gestionar esta evolución se utilizó \textbf{Alembic}, que permite describir cada cambio estructural como un archivo de migración versionado, aplicar o revertir cambios de forma controlada y mantener consistencia entre los entornos de desarrollo y producción.

Se generaron 13 migraciones que documentan el historial completo del esquema. Entre los cambios más relevantes desde el punto de vista de ingeniería destacan dos. El primero fue la \textbf{conversión de columnas monetarias de \texttt{DOUBLE} a \texttt{NUMERIC}}: durante el desarrollo inicial se usó \texttt{DOUBLE} por simplicidad, pero al verificar el comportamiento de las operaciones de suma se detectaron diferencias de centavos en los totales acumulados, problema propio de la aritmética de punto flotante; la migración corrigió el tipo de dato en todas las tablas afectadas sin pérdida de información. El segundo fue la \textbf{adición de \texttt{deleted\_at}} a múltiples tablas en migraciones separadas, a medida que el análisis de los flujos del sistema reveló que la eliminación física de registros rompía vínculos necesarios para la integridad del historial.

Este proceso iterativo demuestra que el diseño de la base de datos fue resultado de un ciclo continuo de verificación y corrección, y no de una especificación completamente definida desde el inicio.
